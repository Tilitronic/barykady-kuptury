## 1. Environment decision (firm)

**Use the real local Supabase stack as the backend**, not a from-scratch Bun clone of
PostgREST.

Why:
- Docker `29.6.1` is available and the Supabase CLI is already a project dependency
  (`pnpm --dir apps/web/barykadyKultury exec supabase …`).
- The app talks to PostgREST through `@supabase/supabase-js`; a Bun re-implementation
  would have to clone `select`, embedded relations, `eq/in/is/not`, ordering, limits,
  Auth and Storage semantics — that is a second backend that will drift from the real
  one, exactly where RLS and auth are the things we need to test.
- Sessions 3–6 already validated migrations, RLS and the seed against a local stack.
- The admin block (T-026…T-031) needs real RLS and real JWTs; a mock would give false
  confidence.

**Bun is used where it is genuinely needed:** a small mock server for the Google
Calendar adapter (no Google credentials exist), plus the demo asset uploader and
one-command orchestration scripts. If Docker ever becomes unavailable, a full Bun
mock backend is a documented fallback — not built now (YAGNI).

## 4. Bun calendar mock

- Endpoint path identical to production: `/.netlify/functions/calendar-events`.
- Reuses the T-023 normalizer/handler by relative import (Bun runs TS directly; no `@/`
  alias).
- Deterministic `generatedAt`, injected clock, CORS for the dev origin.
- Scenarios via `?scenario=`:
  `default` (5 events), `empty` (0), `unavailable` (502 `calendar_unavailable`),
  `dense` (20 events for list stress), `long` (long pl/uk titles at 320 px),
  `dst` (Europe/Warsaw spring-forward boundary).
- Vite dev proxy maps the production path to the mock, so the SPA and its tests keep one
  same-origin contract and production wiring does not change.

## 8. Risks

| Risk | Mitigation |
|---|---|
| Docker/WSL slowness or port clashes | Documented ports; `demo:stop`; `demo:check` fails fast with a clear message |
| Service-role key leaking into the repo/client | Read it at runtime from local `supabase status`; never write it to `.env.local`; never `VITE_*` |
| Demo data mistaken for real content | Fictional labels in copy; `docs/DEMO_ENVIRONMENT.md` warning; separate `seed.demo.sql` not referenced by build/CI |
| Bun mock drifting from the real adapter | Import the same handler/normalizer; assert the wire shape in `demo:check` |
| Vite proxy leaking into production | Proxy added only in the dev block; production build unchanged |
| Admin work blocking on auth | Lane A creates the demo users first; T-026 can start with the layout once users exist |

## 9. Security note from this handoff preparation

`NGOinfoSources/` is now ignored and removed from the index (`d7b1c8e`) — the local
files are untouched. **However, the folder is already present in pushed history**
(`bec10ba` is an ancestor of `origin/main`). `govIds.txt` and `kontactData.txt` are
therefore publicly retrievable from git history. Untracking only prevents future
changes. If that material is sensitive, the hosting phase must start with a coordinated
history purge (`git filter-repo`), a force-push, and rotation/review of anything those
files contain — decide before the next push. Brand logo copies remain in
`src/assets/brand/`, so the app does not depend on the ignored folder.
